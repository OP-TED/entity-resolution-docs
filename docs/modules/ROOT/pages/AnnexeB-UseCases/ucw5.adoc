== UC-W5  Manage Curator Access

*Use Case Level:* White (Summary) +
*Primary Actor:* Admin (application role) +
*Scope:* Link Curation Application +

*Stakeholders and Interests*

* Admins require a simple and reliable mechanism to control who can access curator functionality within the Link Curation application.
* Curators require predictable access behaviour, including timely provisioning and immediate suspension when access is revoked.
* Originators and downstream consumers indirectly depend on controlled curator access to ensure that re-evaluation actions are performed only by authorised users.

*Goal / Value* +
Provide minimal and controlled curator user management so that access to curation functionality can be granted, modified, suspended, reactivated, or retired in a consistent and reversible way, independently of the underlying authentication mechanism. +

*Scope (System-of-Interest)* +
The Link Curation application, limited to:

* maintaining a registry of users permitted to act as Curators or Admins,
* associating authenticated user identities with application roles,
* activating and deactivating curator access.
How user identities are authenticated (for example via Single Sign-On, external identity provider, or locally managed credentials) is outside the scope of this use case. +

*Out of Scope*

* Credential storage and password management.
* Configuration of external identity providers or SSO infrastructure.
* Advanced identity governance workflows (approvals, recertification, role mining).
* Fine-grained authorisation beyond the defined application roles.

*Brief Description* +
This use case describes how an Admin manages curator access within the Link Curation application. +
User management is role-based and lightweight. The system recognises authenticated users and determines whether they are allowed to perform curator actions based on their assigned role. +

The Admin may:

. Grant curator access to an identified user.
. Modify an existing role assignment.
. Suspend curator access, preventing further interaction with curation functionality.
. Reactivate previously suspended access.
. Retire access permanently while retaining historical references to the user for traceability of past actions.

Suspension or retirement of access takes effect immediately. +
Curator access management does not modify Cluster Assignments, Decision Store content, or any canonical identity state. +

*Success Guarantees (Postconditions)*

* The requested role change is applied consistently and reflected in subsequent access checks.
* Suspended or retired users cannot perform curator actions.
* Historical references to user identifiers remain available for traceability of past re-evaluation actions.

*Minimal Guarantees (On Failure)*

* If an access management operation fails, no partial or ambiguous access state is exposed.
* The system reports the failure to the Admin and does not grant unintended access.

*Special Requirements*

* Access control is role-based and limited to defined application roles (e.g. Admin and Curator).
* Access management is independent of clustering logic, resolution processing, and canonical identity semantics.
* The design must remain compatible with both externally managed authentication (e.g. SSO) and locally managed authentication.

*Frequency of Occurrence* +
Low; invoked when onboarding, modifying, or removing curator access.
