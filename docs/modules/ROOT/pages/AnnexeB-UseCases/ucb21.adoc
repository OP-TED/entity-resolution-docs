= UC-B2.1: Submit Re-evaluation Request

*Use Case Level:* Blue (User-goal) +
*Primary Actor:* Curator (human user) +
*Supporting Actors:* Entity Resolution System (ERSys); Entity Resolution Engine (ERE); Decision Store (latest Cluster Assignment per mention) +
*Scope:* Link Curation Application and ERS User Interaction Interface

// Original primary actor read "Authorised User (e.g. Curator or Operational Reviewer)"; aligned to the glossary preferred term "Curator" ("reviewer" is a listed alternative). This is the Blue refinement of UC-W2 (Curator).

This Blue use case refines xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2: Recommend Resolution Update (Curation)] for the single-mention path. The engine-authoritative contract is stated in UC-W2; this page states the realisation specifics of the Link Curation submission path.

== Stakeholders and Interests

* The Curator requires a controlled mechanism to request re-evaluation of a single mention's Cluster Assignment through the Link Curation application.
* Originators and downstream consumers require that any change in canonical identity remains consistent with the engine-authoritative model and observable through standard synchronisation mechanisms.
* ERS operators require that user actions do not introduce independent governance semantics or override engine authority.

== Brief Description

This use case describes the processing of a Curator-initiated re-evaluation request under the engine-authoritative clustering model. The engine-authoritative contract (canonical identity definition, ERE authority, recommendation-not-override semantics) is stated in xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2] and is not restated here.

The goal is to allow a Curator to request re-evaluation of the current Cluster Assignment of a single Entity Mention by submitting a placement recommendation or exclusion list for forwarding to ERE.

The Curator may perform one of the following actions:

. *Placement Recommendation* — recommending assignment of the mention to a specified cluster.
. *Exclusion Recommendation* — requesting re-resolution with one or more clusters excluded from consideration.

Upon submission:

* ERS validates the request.
* ERS forwards the recommendation to ERE using the appropriate interaction type.
* ERS does not modify the current Cluster Assignment at this stage.

ERE evaluates the recommendation according to its internal clustering logic and returns an authoritative clustering outcome asynchronously. Only after receiving the authoritative outcome from ERE does ERS update the Decision Store to reflect the latest Cluster Assignment.

== Preconditions

* The Entity Mention exists in the Decision Store and has a current Cluster Assignment.
* The system can retrieve the latest clustering context stored in the Decision Store, including:
** the Entity Mention representation,
** the current Cluster Assignment (cluster identifier),
** the top N alternative clusters returned by the latest ERE outcome.
* The Curator is authenticated and authorised to submit re-evaluation requests.

== Trigger

The Curator selects an existing Entity Mention in the Link Curation application and chooses to request re-evaluation of its Cluster Assignment.

== Success Guarantee (Postconditions)

The contract-level success and minimal guarantees, the outcome possibilities (unchanged / different existing cluster / new cluster), and the placement/exclusion scenarios are those of xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2] and are not restated here. This Blue single-mention path adds only the following realisation specifics:

. The Curator request is accepted and forwarded to ERE; no immediate change to the stored Cluster Assignment occurs until ERE responds asynchronously.
. Only after receiving the authoritative outcome from ERE does ERS update the Decision Store, after which any change updates delta tracking for refresh operations.

== Minimal Guarantees (On Failure)

As stated in xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2], with the realisation specific that if ERS cannot forward the request to ERE, the current Cluster Assignment remains unchanged and no intermediate state is created.

== Special Requirements

The UC-W2 special requirements (recommendation-not-override, binding ERE decisions, latest-assignment-only with no canonical lineage, delta tracking on change) apply. No additional Blue-specific special requirements arise for the single-mention path.

== Technology and Data Variations

The interaction mechanism between the Link Curation application and ERS may vary by deployment. Message formats and interaction types are defined in the xref:ERS-ERE-Contract/interface.adoc[ERS–ERE contract].

== Frequency of Occurrence

Low to medium; invoked when manual review or operational correction is required.
