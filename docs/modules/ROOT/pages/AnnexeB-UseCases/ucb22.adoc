= UC-B2.2: Submit Bulk Re-evaluation

*Use Case Level:* Blue (User-goal) +
*Primary Actor:* Curator (human user) +
*Supporting Actors:* Entity Resolution System (ERSys); Entity Resolution Engine (ERE); Decision Store (latest Cluster Assignment per mention) +
*Scope:* Link Curation Application and ERS Curator Interaction Interface (bulk mode)

This Blue use case refines xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2: Recommend Resolution Update (Curation)] for the bulk path. The engine-authoritative contract is stated in UC-W2; this page states the realisation specifics of bulk submission.

== Stakeholders and Interests

* The Curator requires a controlled mechanism to request re-evaluation of multiple mentions in a single bulk operation through the Link Curation application.
* Originators and downstream consumers require that any change in canonical identity remains consistent with the engine-authoritative model and observable through standard synchronisation mechanisms.
* ERS operators require that bulk curator actions do not introduce independent governance semantics or override engine authority.

== Brief Description

This use case describes the processing of a Curator-initiated bulk re-evaluation request under the engine-authoritative clustering model. The engine-authoritative contract (canonical identity definition, ERE authority, recommendation-not-override semantics) is stated in xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2] and is not restated here.

The goal is to allow a Curator to request re-evaluation of multiple Entity Mentions in a single bulk operation by applying a uniform recommendation pattern, without directly modifying canonical identity.

Bulk mode allows the Curator to apply a uniform recommendation to multiple mentions. Supported bulk actions include:

. Submit a common Placement Recommendation for each selected mention.
. Submit a common Exclusion Recommendation for each selected mention.

Bulk processing is defined as a set of independent single-mention re-evaluation requests. No shared clustering semantics are introduced across mentions.

Upon submission:

* ERS validates the bulk request.
* For each selected mention, ERS forwards the corresponding recommendation to ERE using the appropriate interaction type.
* ERS does not modify any Cluster Assignment at submission time.

ERE evaluates each mention independently and returns authoritative clustering outcomes asynchronously. ERS updates the Decision Store per mention only after receiving authoritative outcomes from ERE.

== Preconditions

* Each selected Entity Mention exists in the Decision Store and has a current Cluster Assignment.
* The system can retrieve the clustering context for each selected mention.
* The Curator is authenticated and authorised to submit bulk re-evaluation requests.

== Trigger

The Curator selects multiple Entity Mentions in the Link Curation application and initiates a bulk re-evaluation action.

== Success Guarantee (Postconditions)

The per-mention contract-level success and minimal guarantees are those of xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2], applied independently to each mention and not restated here. The bulk path adds only the following realisation specifics:

. Each selected mention is forwarded to ERE and processed independently; the Decision Store is updated per mention only after the corresponding authoritative ERE outcome, and any change updates delta tracking for refresh operations.
. Bulk submission supports partial success: each mention succeeds or fails independently.

== Minimal Guarantees (On Failure)

Per mention, as stated in xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2]. The bulk-specific guarantee is that invalid or ineligible mentions are rejected individually while others may proceed, and a forwarding failure for one mention leaves that mention's Cluster Assignment unchanged with no intermediate state created.

== Main Success Scenario

. The Curator selects multiple mentions and chooses a bulk re-evaluation action.
. ERS validates each selected mention.
. ERS forwards individual recommendations for each mention to ERE.
. ERE evaluates each mention independently and returns authoritative clustering outcomes.
. ERS updates the Decision Store per mention to reflect the resulting Cluster Assignments.

== Extensions

1a. Partial validation failure — Invalid mentions are rejected individually; valid mentions proceed. +
2a. Concurrent modification detected — If a mention has already been updated by a separate operation, ERS applies correlation rules and forwards the request; the authoritative outcome from ERE prevails. +
3a. No change in outcome — ERE confirms the existing Cluster Assignment; because the recorded assignment does not change, no delta update occurs.

== Special Requirements

* Bulk re-evaluation introduces no governance override semantics.
* ERE decisions are binding.
* Each mention is processed atomically and independently.
* ERS stores only the latest Cluster Assignment per mention and does not maintain canonical lineage.
* All resulting Cluster Assignment changes must update delta tracking.

== Technology and Data Variations

The bulk interaction mechanism may vary by deployment. Message formats and interaction types are defined in the xref:ERS-ERE-Contract/interface.adoc[ERS–ERE contract].

== Frequency of Occurrence

Low to medium; used for operational efficiency when reviewing multiple related mentions.
