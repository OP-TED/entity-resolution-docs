== 10 Interface traceability and dependency inventory

This section provides a concise, interface-oriented traceability view across ERSys. It enumerates the externally visible operations exposed by each interface family and records their downstream dependencies, where applicable, together with the key conceptual data objects exchanged. The purpose is to make explicit how actions taken through one interface propagate across others, without restating behavioural sequencing or contractual detail already defined elsewhere.

=== 10.1 Dependency inventory by interface

The dependency inventory is organised by interface family. Each table lists the primary operations exposed by that interface, the upstream trigger, any downstream dependencies on other interfaces, and the principal data objects exchanged. Responses are treated as part of the same operation and are not listed separately. +
*ERS REST interface (client-facing)*
|===
|*Operation*|*Upstream trigger*|*Downstream dependency*|*Key data objects exchanged*

|Resolve Entity Mention|Originator submits resolution request|Triggers asynchronous EntityMentionResolutionRequest on ERS–ERE interface|EntityMentionIdentifier (sourceId, requestId, entityType), EntityMention; response returns clusterId and entityMentionContext
|Lookup current canonica Id|Originator or downstream consumer requests current placement|None (read-only)|EntityMentionIdentifier; response returns current clusterId
|Bulk refresh / lookup (delta synchronisation)|Originator or downstream consumer requests updates since last exposure|None (read-only)|sourceId, optional limit; response returns list of updated clusterId values and optional continuationCursor
|===
The ERS REST interface provides bounded, synchronous interactions. Only the Resolve operation has downstream effects, by initiating asynchronous resolution. Lookup operations are strictly read-only and do not trigger further processing. +
*Link Curation REST interface*
|===
|*Operation*|*Upstream trigger*|*Downstream dependency*|*Key data objects exchanged*

|Get Decisions|Curator requests projection list|None (read-only)|Decision (updatedAt, current ClusterReference, candidate ClusterReference[])
|Preview Entity Mention|Curator requests inspection of mention|None (read-only)|EntityMentionIdentifier, EntityMention, optional JSONRepresentation
|Preview Canonical Entity|Curator requests inspection of canonical placement|None (read-only)|clusterId with associated EntityMentionIdentifier list (projection view)
|Submit Decision|Curator submits structured recommendation|Triggers asynchronous EntityMentionResolutionRequest on ERS–ERE interface|EntityMentionIdentifier, userAction (UserActionType), optional targetCluster (ClusterReference)
|Get Statistics|Curator requests aggregated indicators|None (read-only)|Statistics (RegistryStatistics and CurationStatistics aggregates)
|===

Submit Decision does not directly mutate canonical placement. Any change in clusterId occurs only if ERE emits a subsequent EntityMentionResolutionResponse. +
*ERS–ERE asynchronous interface*
|===
|*Operation*|*Upstream trigger*|*Downstream dependency*|*Key data objects exchanged*

|EntityMentionResolutionRequest|Triggered by Resolve (ERS REST) or Submit Decision (Link Curation)|None (engine boundary)|EntityMentionIdentifier, EntityMention, optional proposedClusterId, optional excludedClusterId
|EntityMentionResolutionResponse|Triggered by ERE clustering outcome|Replaces Decision projection within ERS; may render mention eligible for delta exposure|EntityMentionIdentifier, ClusterReference[] (clusterId, confidenceScore, similarityScore)
|===
Asynchronous delivery follows at-least-once semantics. Messages may be duplicated or reordered. ERS integrates responses idempotently based on the correlation triad and replacement semantics of the Decision projection. There is no explicit cluster rebuild command. Reclustering inside ERE is internal. Any resulting changes are communicated exclusively through standard resolution responses.

=== 10.2 Cross-interface dependency and anchoring notes

The dependencies recorded above reflect the stable architectural relationships between interfaces:

* Resolve initiates asynchronous clustering while preserving the correlation triad and Entity Mention payload.
* Submit Decision forwards human recommendations to ERE without bypassing engine authority.
* EntityMentionResolutionResponse replaces projection state and updates Decision.updatedAt, enabling delta exposure.
* Read-only operations (lookup, preview, statistics, refreshBulk) never trigger engine processing.
All operations and data objects referenced in this section are anchored to the conceptual information models defined in Section 9. Behavioural sequencing is defined in Section 8. Normative schema and protocol details are defined in the corresponding interface and messaging contracts.
