=== 8.2 Spine A: Resolution intake and canonical identifier issuance

Spine A defines the client-facing *Resolve* interaction in which an Originator submits a single Entity Mention and receives an identifier within the client-facing time budget. This spine exists to make three things unambiguous at the ERS boundary:

* *Idempotent intake* correlated by the triad _(sourceId, requestId, entityType)_.
* *Dual time budgets*, where the ERS ↔ ERE execution window is shorter than the client ↔ ERS timeout budget.
* *Identifier availability semantics*, including the provisional singleton lifecycle when the engine does not respond in time.

*Narrative aligned to the simplified diagram* +

*Submit resolve request.* The Originator submits a resolve request containing the triad _(sourceId, requestId, entityType)_ and a single Entity Mention payload to the ERS intake interface. +
*Validate and enforce idempotency.* ERS validates the request and enforces idempotency based on the triad. Replays are handled deterministically. Conflicting submissions, such as reuse of the same triad with a different payload under the same contract rules, are rejected. +
*Reject invalid or non-processable requests.* If the request violates mandatory validation rules, triggers an idempotency conflict, or cannot be processed due to mandatory dependency unavailability, ERS returns an explicit error outcome. +
*Initiate resolution via the async contract.* For an accepted request, ERS publishes a resolution request asynchronously via the messaging middleware. Publication is part of the synchronous interaction, but it does not make the client call “asynchronous”. The client still observes a bounded response. +
*Return within the client budget.* ERS waits up to the *ERS ↔ ERE execution window* for an authoritative engine outcome.

* If an engine outcome is received within the execution window, ERS records the latest decision for the mention and returns the *clusterId (canonical identifier)* produced by the ERE.
* If no engine outcome is received within the execution window, ERS issues a *provisional singleton clusterId*, records it as the current placement for the mention, returns it to the client within the client budget, and forwards the provisional placement to ERE as a standard resolution request variant using *recommendedPlacement*.
* If the *client ↔ ERS timeout budget* is exceeded before ERS can produce a compliant response, ERS returns an explicit timeout or error outcome.
*Late and duplicate outcomes.* Engine outcomes may arrive late or duplicated. ERS processes them idempotently and updates its stored *latest decision record per mention*. Completed client responses are not retroactively changed, but the canonical identifier exposed by ERS for subsequent lookups and bulk delta synchronisation reflects the latest authoritative assignment recorded. +

*Key behavioural commitments shown*

* Each resolve request is correlated by _(sourceId, requestId, entityType)_ and processes exactly one Entity Mention.
* ERS enforces idempotency at intake: deterministic handling of identical replays; explicit rejection of contract-relevant conflicts.
* The engine boundary is asynchronous and tolerant to at-least-once delivery; duplicates and late arrivals are normalised by idempotent processing.
* An identifier is returned within the client-facing budget when possible:
** authoritative *clusterId* if the engine responds within the ERS ↔ ERE execution window,
** otherwise a *provisional singleton clusterId*, treated as the current canonical placement until replaced by a later authoritative outcome.

*Authoritative state touched*

* *Request Registry* (intake and correlation): stores request records keyed by _(sourceId, requestId, entityType)_ sufficient to detect replays, reject idempotency conflicts, and support deterministic processing.
* *Decision Store* (latest decision per mention): stores the latest recorded placement (*clusterId*), top N alternatives when provided by the ERE, the contextId used for correlation, and relevant timestamps.
* *Delta tracking fields* (per originId exposure): updated when the recorded placement changes, enabling refreshBulk to expose changes consistently.

* *Blue Use Case(s):* UC-B-1.1.
