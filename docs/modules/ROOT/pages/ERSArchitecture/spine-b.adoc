=== 8.3 Spine B: Asynchronous engine interaction and outcome integration (ERS - ERE)

Spine B defines the asynchronous interaction between ERS and the Entity Resolution Engine (ERE) for resolution requests and clustering outcomes. This spine is the architectural “shock absorber” of ERSys: it makes explicit that messaging is at-least-once, outcomes can be late or duplicated, and the engine may publish outcomes even when ERS did not just send a request (for example, due to engine-initiated reclustering). The key point is simple: the ERE is authoritative for clustering outcomes, and ERS is responsible for correlating, recording, and exposing the latest outcome per mention. +

*Narrative aligned to the simplified diagram* +

*Publish a resolution request (asynchronous).* ERS may publish a resolution request to the messaging middleware. This is typically triggered by Spine A (intake) or Spine D (curation recommendation), and it always carries the correlation triad _(sourceId, requestId, entityType)_ plus the Entity Mention. +
Optionally, ERS may include additional request metadata that shapes how the engine evaluates the case:

* *recommendedExclusions* (negative evidence), and/or
* *recommendedPlacement* (preferred clusterId), including provisional singleton placement.
These fields are not “governance overrides”. They are inputs to engine evaluation.+
*Deliver to the engine under at-least-once semantics.* The messaging middleware delivers the request to the ERE asynchronously. Duplicates can occur, and delivery ordering is not guaranteed. +
*Produce and publish an authoritative outcome.* The ERE performs its internal resolution logic and publishes a resolution result that includes:

* the correlation triad _(sourceId, requestId, entityType)_,
* the primary *clusterId (canonical identifier)*,
* top alternative clusterIds
* For each cluster the related scoring metadata: confidence and similarity scores.

Outcomes may be *solicited* (in response to an ERS request) or *unsolicited* (for example, engine-initiated reclustering). Both are handled using the same integration pattern. +

*Validate, correlate, and record.* ERS validates the message envelope and schema against the ERS–ERE Technical Contract.

* If the delivery violates the contract (for example, missing triad, invalid schema), ERS records the violation for traceability and ignores the payload for decision state.
* If the delivery is acceptable (including duplicates or late arrivals), ERS correlates by the triad and updates its *latest decision record per mention*. This includes recording the current clusterId, top alternatives (as provided), contextId for correlation, and timestamps.
*Expose “latest assignment wins”.* Completed client responses are not retroactively rewritten. However, subsequent lookups and refreshBulk delta exposure reflect the latest authoritative assignment recorded by ERS. In other words: the HTTP response is fixed, but the canonical identity exposed by the system may evolve as the engine publishes improved outcomes. +
*Ordering and deduplication rule (normative).* ERS shall treat ERE outcomes as _idempotent but not ordered_. For a given triad, ERS shall accept an outcome only if it is not stale with respect to the currently recorded decision. Staleness shall be determined using a contract-defined monotonic outcome marker (e.g., engineOutcomeTimestamp or engineOutcomeSequence) produced by the engine. If the marker indicates the outcome is older than the stored one, ERS shall ignore it for decision state (but may record it for operational traceability). +

*Key behavioural commitments shown*

* ERS–ERE communication is *exclusively asynchronous* and governed by the ERS–ERE Technical Contract.
* ERE outcomes are *authoritative clustering outcomes*, not advisory proposals.
* Correlation and idempotent absorption are performed using the triad _(sourceId, requestId, entityType)_, and the integration is tolerant to duplicates and late arrivals.
* Optional *recommendedExclusions* and *recommendedPlacement* are treated as input evidence. The ERE remains binding for the resulting cluster assignment.
* ERS records and exposes only what it needs: the *latest decision record per mention* (current clusterId, alternatives, contextId, timestamps). There is no Canonical Entity Registry or canonical lineage store inside ERS.

*Authoritative state touched*

* *Decision Store* (latest decision per mention): updated on acceptable outcome deliveries (including late or duplicate deliveries) to reflect the latest recorded assignment.
* *Contract violation log / operational trace*: updated when invalid deliveries are received (for investigation and robustness), without mutating decision state.
* *Request Registry*: not mutated by Spine B; used implicitly for correlation and idempotency handling.

*Traceability*

* *White Use Case(s):* UC-W1 (asynchronous completion and late outcomes), UC-W2 (recommendations triggering re-evaluation).
* *Blue Use Case(s):* UC-B-1.2.
* *ADRs:* ADR-A1N, ADR-A2N, ADR-C1N, ADR-C2N, ADR-C3N (engine authority, provisional lifecycle, idempotency, at-least-once tolerance, and integration semantics).
* *Contracts:* ERS–ERE Technical Contract (asynchronous, normative).
