= Core System Capabilities (White Use Cases)

This section summarises the core behavioural capabilities of ERSys through a small set of White Use Cases.

White Use Cases are normative: they define what ERSys guarantees to its actors and what can be observed at the system boundary, independently of internal algorithms, storage technology, or deployment choices. Long-form use case narratives are not duplicated in the main architecture text, to prevent divergence.

*Authoritative specification location.* The full, normative White and Blue Use Case texts are maintained in xref:AnnexeB-UseCases/index.adoc[Annexe B (Use Case Catalogue)]. This section provides an architectural digest and traceability anchors:

* which capability exists and why it matters,
* which actor triggers it,
* which guarantees are externally observable,
* which contracts and spines realise it.

The scope here is deliberately limited to the *resolution lifecycle under the engine-authoritative clustering model*:

* submission of entity mentions and bounded identifier issuance,
* curator recommendations that trigger re-evaluation, without turning curation into an override layer,
* client synchronisation via delta exposure (refreshBulk), because assignments can change after the initial response,
* read-only consultation of aggregated statistics.

Operational concerns such as user management, authentication technology, monitoring, and deployment automation are intentionally excluded from this section and addressed in dedicated security and operations artefacts.

*Important boundary note.* Reprocessing and rebuild are *ERE-internal* concerns. ERSys does not expose a rebuild service as a first-class administrative capability. When the engine reprocesses and produces updated clustering outcomes, those outcomes flow through the standard asynchronous responses channel and become observable to clients through the same delta mechanisms as any other assignment change.

== Resolve Entity Mention (UC-W1)

*Purpose and value:* xref:AnnexeB-UseCases/ucw1.adoc#uc-w1[UC-W1] defines the primary capability that makes ERSys useful for interoperability: an originator submits an *Entity Mention* (a description artefact) and receives a *`cluster_id` (canonical identifier)* that can be used immediately as a stable reference in downstream pipelines. Entity resolution is computationally variable and sometimes slow, while client integrations typically enforce strict timeouts. UC-W1 therefore expresses a bounded, client-facing contract that keeps the API predictable, while still respecting the engine-authoritative clustering model.

*Primary actor:* API Client (Originator).

*Trigger:* The Originator calls the ERS resolve operation for one Entity Mention.

*Entry point and contracts*

* *Interface*: ERS public REST API (Resolve).
* *Engine boundary*: ERS–ERE asynchronous technical contract for resolution requests and outcomes.
* *Correlation key (triad)*: _(source_id, request_id, entity_type)_.

*Success outcomes (externally observable)* +
On success, the Originator observes that:

* ERS returns a *`cluster_id` (canonical identifier)* within the *client–ERS timeout budget*.
* The returned identifier is within the *single identifier value space* used by ERSys (no secondary canonical registry identifiers).
* If the ERE responds within the *ERS–ERE execution window*, ERS returns the *`cluster_id` produced by the ERE*.
* If the ERE does not respond within the ERS–ERE execution window, ERS returns a *provisional singleton `cluster_id`* (still a valid canonical identifier at the moment of response) and submits the corresponding recommended placement to ERE for authoritative evaluation.

*Failure outcomes (externally observable)* +

If the request cannot be accepted or processed, the Originator observes that:

* ERS returns an explicit error response (validation and contract errors are first-class).
* ERS does not claim that identity was established when it was not: there is no silent success and no ambiguous outcome.

*Rules and invariants that constrain UC-W1*

* *Engine authority*: the ERE is authoritative for clustering outcomes and canonical identity materialisation; ERS does not decide equivalence, it records and exposes outcomes.
* *Dual time budgets*: the client–ERS budget is enforced at the REST boundary; the ERS–ERE execution window is shorter and drives provisional issuance.
* *Provisional lifecycle is normal*: a canonical identifier may change after the initial response if the ERE later replaces the provisional assignment; this is expected and is reconciled via refreshBulk and subsequent lookups.
* *Idempotency and correlation*: processing is correlated by the triad and must tolerate retries and at-least-once delivery patterns without creating inconsistent double state.
* *Latest outcome wins (projection semantics)*: ERS exposes the latest authoritative cluster assignment it has recorded for the mention.

*State touched (ERS-owned)*

* *Request Registry*: records acceptance of the mention and the correlation metadata required for idempotency and traceability.
* *Decision Store*: updates the *latest decision record per mention*, including the current `cluster_id`, top N alternatives (when provided by ERE), `context_id`, and relevant timestamps.
* *Delta tracking*: updates the `last_update_date` used by refreshBulk whenever the recorded placement changes.

*Behavioural spine mapping*

* Realised primarily by *Spine A* (bounded intake and identifier issuance) and *Spine B* (asynchronous engine outcomes, including late outcomes and provisional replacement).

*Authoritative detailed specification*

* Full normative text and extensions: xref:AnnexeB-UseCases/ucw1.adoc#uc-w1[UC-W1] and related Blue UCs.
* Contract realisations: ERS OpenAPI (Resolve) and the ERS–ERE Technical Contract.

== Recommend Resolution Update (UC-W2)

*Purpose and value* +
xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2] captures the human-in-the-loop capability of ERSys under the engine-authoritative clustering model. A curator does not override canonical identity directly. Instead, the curator provides *recommendations* that act as additional evidence: preferred placement, negative constraints, or both. ERS records these actions for traceability and forwards them to the ERE using the same asynchronous contract pattern as any other resolution interaction. This allows humans to correct or refine difficult cases while keeping the system semantics clean and interoperable: the ERE remains the single authority for the resulting clustering outcome.

*Primary actor:* Curator (human user), acting via the Link Curation Web Application.

*Trigger:* The curator selects an existing mention (or a set of mentions) and submits a recommendation to re-evaluate its current cluster placement.

*Entry point and contracts*

* *Interface*: Link Curation REST API exposed by ERS (curation operations).
* *Engine boundary*: ERS–ERE asynchronous technical contract.
* *Correlation key (triad)*: _(source_id, request_id, entity_type)_.

*Success outcomes (externally observable)* +
On success, the curator observes that:

* ERS accepts a recommendation that is explicitly tied to a known mention (by triad) and acknowledges it.
* The recommendation is expressed using the optional ERS→ERE fields `proposed_cluster_ids` and/or `excluded_cluster_ids` defined in the xref:ERS-ERE-Contract/interface.adoc[ERS–ERE contract].
* ERS forwards the recommendation to the ERE as a standard resolution request variant, preserving correlation and idempotency semantics.
* Once the ERE produces a new clustering outcome, ERS records the *latest cluster assignment per mention* and exposes it through lookup and refreshBulk.
* The curator can later observe the updated placement (or lack of change) through the same read-only mechanisms as any other client.

*Failure outcomes (externally observable)* +
If the recommendation cannot be accepted or processed, the curator observes that:

* ERS returns an explicit error (unknown mention, invalid `cluster_id` references, or malformed request).
* No partial state is exposed as if it were authoritative; recommendations are not half applied.

*Rules and invariants that constrain UC-W2*

* *Recommendations are not authority*: curator actions do not directly modify canonical identity. They are inputs to ERE evaluation.
* *Engine authority remains binding*: the ERE may accept or revert the recommendation; the resulting cluster assignment is authoritative.
* *Same pattern as provisional placement*: recommendations are transmitted as resolution requests, not as a special governance backdoor.
* *At-least-once tolerance and idempotency*: duplicate deliveries or retries must not create inconsistent recorded outcomes.
* *Latest outcome wins (projection semantics)*: ERS exposes the latest authoritative outcome it has recorded for the mention.

*State touched (ERS-owned)*

* *User Action Log*: records the curator's recommendation as a read-only trace (training and accountability oriented).
* *Decision Store*: updates the latest decision record per mention when an authoritative engine outcome is received (current `cluster_id`, top N alternatives when provided, `context_id`, timestamps).
* *Delta tracking*: if the recorded placement changes, the change becomes eligible for refreshBulk delta exposure.

*Behavioural spine mapping*

* Realised primarily by *Spine D* (curation as a recommendation submission) and *Spine B* (engine re-evaluation outcomes and their integration).

*Authoritative detailed specification*

* Full normative text and detailed flows: xref:AnnexeB-UseCases/ucw2.adoc#uc-w2[UC-W2] and related Blue UCs.
* Contract realisations: ERS OpenAPI (Link Curation endpoints) and the ERS–ERE Technical Contract.

== Synchronise Resolution Updates (UC-W3)

*Purpose and value* +
xref:AnnexeB-UseCases/ucw3.adoc#uc-w3[UC-W3] defines the practical reconciliation mechanism that makes the engine-authoritative model workable for real integrations. Because clustering outcomes can arrive late and a mention-to-cluster assignment may change over time (including through engine-initiated reclustering), a client needs a predictable way to ask what changed since it last checked. refreshBulk is that mechanism. It is deliberately pull-based and delta-oriented, because push notifications tend to create hidden coupling and brittle delivery guarantees. Clients keep using `cluster_id` as the canonical identifier and periodically synchronise changes using refreshBulk; this reconciliation path also reflects engine reclustering outcomes.

*Primary actor:* API Client acting as Downstream Consumer (and in some cases also the Originator).

*Trigger:* The client calls the ERS refreshBulk operation for a given `source_id` to retrieve placement changes not previously exposed to that `source_id`.

*Entry point and contracts*

* *Interface*: ERS public REST API (refreshBulk).
* *Correlation*: results are expressed in terms of Entity Mention identifiers (triad) and their current `cluster_id`.
* *No engine contract dependency at call time*: refreshBulk is served from ERS state; it does not synchronously depend on ERE availability.

*Success outcomes (externally observable)* +
On success, the client observes that:

* ERS returns a list of mentions whose recorded placement *changed* since the last successful notification point for that `source_id`.
* Each returned item includes the key correlation and resolution fields needed for downstream reconciliation, typically:
** the correlation triad and/or `request_id` as defined by the API contract,
** the current `cluster_id`,
** `context_id` (for correlation with engine outcomes),
** timestamps relevant to delta semantics.
* The delta rule is timestamp-based and stable: `last_notification_date` < `last_update_date`.
* Changes may originate from multiple sources, and refreshBulk treats them uniformly:
** initial resolve outcomes,
** engine-initiated reclustering (unsolicited outcomes),
** curator recommendations leading to re-evaluation,
** replacement of provisional placement by a later engine outcome.

*Failure outcomes (externally observable)* +
If refreshBulk cannot be served, the client observes that:

* ERS returns an explicit error (authorisation failure, invalid `source_id`, temporary unavailability).
* No state is partially advanced. In particular, ERS must not move the notification watermark forward unless a response is successfully produced according to the API contract.

*Rules and invariants that constrain UC-W3*

* *Delta semantics are about placement, not about engine events*: refreshBulk is driven by changes in the recorded mention-to-cluster assignment.
* *Latest outcome wins*: the current `cluster_id` exposed for a mention is the latest authoritative assignment recorded by ERS.
* *No push guarantee is implied*: refreshBulk is the supported synchronisation mechanism; clients should not assume callbacks or notifications.
* *At-least-once tolerance upstream*: engine outcomes may arrive late or duplicated, but refreshBulk exposes a clean, deduplicated view based on recorded state.
* *Scope is per `source_id`*: exposure history is tracked per client `source_id`; different consumers can observe deltas independently.

*State touched (ERS-owned)*

* *Decision Store*: provides the current recorded placement per mention and the timestamps used for delta computation.
* *Delta tracking state*: maintains, per `source_id`, the last successful notification watermark (`last_notification_date`) and updates it only on successful refreshBulk completion.
* *Request Registry*: may be used to validate mention identifiers and preserve traceability, but refreshBulk does not change request records.

*Behavioural spine mapping*

* Realised by *Spine C* (bulk-delta read-only synchronisation), and depends indirectly on *Spine B* because any recorded placement change originates from engine outcomes.

*Authoritative detailed specification*

* Full normative text and edge cases (including large responses and continuation strategy): xref:AnnexeB-UseCases/ucw3.adoc#uc-w3[UC-W3] and related Blue UCs.
* Contract realisation: ERS OpenAPI (refreshBulk) and the conceptual Decision Record Model used for timestamps and correlation fields.

== Consult Resolution Statistics (UC-W4)

*Purpose and value* +
xref:AnnexeB-UseCases/ucw4.adoc#uc-w4[UC-W4] provides lightweight situational awareness for human operators. Operating an entity resolution capability requires answers to simple questions: how much is pending, whether unresolved cases are accumulating, and whether the system is active, quiet, or in churn. UC-W4 covers this without turning ERSys into an analytics platform. The statistics are intentionally limited to aggregated counts and simple indicators that help prioritise curation and spot operational anomalies, while keeping record-level content and identity assignments protected.

*Primary actor:* Curator (human user), acting via the Link Curation Web Application.

*Trigger:* The curator requests a read-only statistics view, typically scoped by `entity_type` and optionally by a time window.

*Entry point and contracts*

* *Interface*: Link Curation REST API exposed by ERS (statistics endpoint).
* *Data source*: derived from ERS-owned stores (Decision Store and User Action Log), not from engine internals.
* *No engine contract dependency at call time*: statistics are served from ERS state; ERE availability is not a synchronous dependency.

*Success outcomes (externally observable)* +
On success, the curator observes that:

* ERS returns an aggregated, read-only summary of the current observable state of resolution and curation activity.
* The result can be scoped by `entity_type` and may include simple indicators such as:
** volume of mentions processed,
** volume of placement changes observed recently,
** counts of items requiring attention (for example, those with low confidence or marked for review, if such a categorisation is part of the contract),
** counts of curator actions recorded over a period.
* The response does not expose individual mentions, individual `cluster_id` values, candidate lists, or any record-level payload content.

*Failure outcomes (externally observable)* +
If statistics cannot be retrieved, the curator observes that:

* ERS returns an explicit error indicating temporary unavailability or authorisation failure.
* No authoritative state is changed; the operation remains strictly read-only.

*Rules and invariants that constrain UC-W4*

* *Read-only by construction*: the UC must not mutate decision state, placements, or delta tracking.
* *No canonical registry semantics*: statistics are not based on a separate canonical registry, and they do not imply an independent lifecycle of canonical entities inside ERS.
* *Indicative, not compliance-grade*: these indicators support operational oversight; they are not audit evidence and not a regulatory trace.
* *Eventual consistency is acceptable*: during high churn (for example, when the ERE publishes reclustering outcomes), aggregated counts may lag slightly behind the newest recorded decision updates.

*State touched (ERS-owned)*

* *Decision Store (read)*: provides counts and simple aggregations over the latest decision records per mention.
* *User Action Log (read)*: provides aggregate measures of curator activity and recommendation volume.
* *No writes*: UC-W4 does not write to any store.

*Behavioural spine mapping*

* Realised through the Link Curation read-only interaction pattern, and depends indirectly on all other spines because they create the underlying state that is being summarised.

*Authoritative detailed specification*

* Full normative text, metric catalogue, and scoping rules: xref:AnnexeB-UseCases/ucw4.adoc#uc-w4[UC-W4] and related Blue UCs.
* Contract realisation: ERS OpenAPI (statistics endpoint) and the conceptual information model for Decision Records and User Action Logs.

== Relationship to detailed behaviour and architectural decisions

The White Use Cases referenced in this section constitute the normative behavioural contract of ERSys: they define the externally observable capabilities and guarantees that the system must uphold at its boundary, independently of implementation choices.

This section provides an architectural digest for readability and traceability. The *authoritative* use case specifications, including both White and Blue levels, are maintained in xref:AnnexeB-UseCases/index.adoc[Annexe B (Use Cases)].

Detailed behaviour and architectural constraints are refined through the following artefacts, each with a distinct role:

* *Blue Use Cases (Annexe B)* refine White Use Cases into implementable behaviour, while remaining within the same external guarantees.
* *Architecture Decision Records (Annexe C)* define binding architectural decisions and invariants that constrain what designs and implementations are allowed.
* *Behavioural spine diagrams (Section 8)* illustrate architecturally significant interaction patterns and responsibility transfers. They operationalise the use cases and invariants, but they *do not introduce additional guarantees* beyond what is stated in the Use Cases and the ADRs.
* *ERS public API specifications and the ERS–ERE Technical Contract* define the concrete interoperability boundary. They must remain consistent with the use cases and ADRs and must not silently redefine system semantics.

In case of ambiguity between behavioural descriptions, precedence is governed by the authority and precedence-by-concern rules defined in the introduction. As a practical rule: Use Cases define externally observable guarantees, ADRs constrain architectural choices, and this architecture (including spines) must remain a coherent consolidation that does not weaken or contradict them.
