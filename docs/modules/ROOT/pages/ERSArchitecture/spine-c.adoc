=== 8.4 Spine C: Canonical assignment lookup (bulk-delta, read-only observation)

Spine C defines the read-only interaction by which a downstream consumer synchronises placement changes in bulk, using the supported delta mechanism (*refreshBulk*). In the engine-authoritative model, mention-to-cluster assignment can evolve over time due to late outcomes, engine-initiated reclustering, or curator recommendations. This spine therefore makes explicit how clients obtain a bounded set of updates, without triggering resolution and without relying on push callbacks. +
This spine is intentionally about *bounded read access and continuation*, not about lookup of a single mention. It is expressed in UML Sequence notation and focuses on responsibility transfer and state observation at the ERS boundary. +

*Narrative aligned to the simplified diagram* +

*Submit refreshBulk request.* A downstream consumer calls refreshBulk for a given *originId* (the consumer identity used for delta tracking). The request may include an optional limit to bound the response size. +
*Validate request.* ERS validates the request is well-formed and that the caller is authorised to access the given originId scope. +
*Compute the delta slice from ERS state.* ERS reads from its Decision Store the set of mentions whose recorded placement changed since the last successful exposure for that originId. The delta rule is conceptually:

* *lastNotificationDate < lastUpdateDate*
The returned update items include, at minimum, the mention correlation identifiers and the current *clusterId (canonical identifier)*, plus correlation metadata such as contextId as defined by the API contract. +
*Return a bounded slice, with continuation if needed.* If the result set is large, ERS returns a bounded slice and a server-minted *continuationCursor* indicating that more results are available. The consumer may call refreshBulk again with that continuationCursor to obtain the next slice. +
*Continue until complete.* The consumer repeats the continuation call until the response indicates there is no more data. +
refreshBulk is strictly read-only with respect to identity and clustering: it does not trigger resolution, re-resolution, curation, or any form of rebuild. Its only permissible state effect is advancing the exposure watermark for that originId when a slice is successfully produced, so that the same updates are not repeatedly returned as “new”. +

*Key behavioural commitments shown*

* refreshBulk is the primary synchronisation mechanism for downstream systems under mutable assignment semantics.
* The operation is *read-only* with respect to placement decisions. It does not trigger engine work.
* Responses are *bounded* and can be paged safely using a server-minted continuationCursor.
* The exposed canonical identity for each mention is the *latest authoritative cluster assignment* recorded by ERS.
* Consumers must tolerate duplicates and re-ordering across calls, because upstream messaging is at-least-once and placements can change again while a bulk sync is in progress.

*Authoritative state touched*

* *Decision Store* (read): provides the current recorded placement per mention and the timestamps needed for delta computation.
* *Delta tracking state (per originId)*: maintains the exposure watermark (lastNotificationDate) and is updated only on successful response production.
No Canonical Entity Registry exists in ERS. The bulk response is derived directly from the latest decision records per mention. +
