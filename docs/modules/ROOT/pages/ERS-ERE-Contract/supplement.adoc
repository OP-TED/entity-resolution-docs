== Functional requirement coverage matrix

The following table provides a bigger picture by showing how the designed contract between the ERS and the ERE satisfies the functional requirements specified for the entire system in the Product Requirements Document. It allows the tracing of requirement fulfilment and shows how they are handled in the ERS–ERE communication context.

|===
|*Functional requirement*|*How it affects the ERS-ERE contract (a.k.a. required operations)*|*How it’s handled by ERE/the contract*

|Entity resolution (single and bulk resolution) |. Entity resolution request is submitted|. An EntityMentionResolutionRequest is published to the ere_requests channel.
|Entity resolution with proposed placement|* An entity resolution was submitted by the ERS|* The ERE might decide to accept the singleton creation or not.
|Bulk refresh|Handled by ERS, ERE is not affected.|N.A.
|Retrieval of entity data (for Link Curation app)|ERE is not affected, data provided by ERS from its store.|N.A.
|Re-resolve a selected entity mention (refresh)|See _Manual curation: _|
|Recalculate the whole ERE cluster structure|The operation is internal to the ERE, doesn’t affect the contract.|The exact meaning of the operation depends on the  ERE implementation.
|Manual curation: Acceptance / rejection of proposed alignments (Link Curation app)|Manual curation decisions are recorded by the ERS and passed to the ERE as suggestions.|The propagation of the user feedback to the ERE is done through the usual resolution flow, using either proposed_clusters_ids or excluded_cluster_ids  (see the _Entity resolution with proposed placement_ row).
|Manual curation: Acceptance of alternative alignment (Link Curation app)|The ERE is not affected. Same as default acceptance.|N.A.
|Manual curation: presentation of stats of resolution|The ERE is not affected by this.|N.A.
|Manual curation: User management|The ERE is not affected by this.|N.A.
|===

== Configuration

The ERE is configured via YAML, possibly with mechanisms to https://dev.to/mkaranasou/python-yaml-configuration-with-environment-variables-parsing-2ha6[inject environment variables] in YAML files. Here, we list some of the configuration options that any ERE needs to support to tune the interface described in the previous sections. Further configuration might be needed depending on the specific ERE implementation (e.g. Redis connection coordinates). +
*entity_types*: URI list of CETs, ie, the entity types that the ERE supports for resolution. In the initial basic ERE, these will likely be organisations and procedures. +
*resolution_timeout* (integer, seconds): max time the ERE should spend trying to resolve an entity, before being interrupted with a failure. Optionally, multiple time duration formats can be supported for this, eg, accepting values like “1m 5s”. +
*confidence_threshold* (float, range 0-1): Minimal value of similarity score needed for an entity mention to be associated with a canonical entity through a canonical identifier. We however recommend not to use such parameter or keep it near to zero to prevent returning empty resolution responses. The long tail problem is handled by the ERS pruning to top-N options.
