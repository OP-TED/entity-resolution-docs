== The ERE Interface

In this section, we list the ERE channels mentioned above and the requests they support. The data types that the requests exchange are briefly mentioned in this section and formally described in a separate LinkML schema.

=== Requests channel

Name: *ere_requests* +
As mentioned above, this receives ERE requests and internally enqueues them for asynchronous execution. +
Namely, the channel is used to send instances of the +ERERequest+ subclasses in JSON format (see the next section for a description of the interface data model).

=== Responses channel

Name: *ere_responses* +
This is the counterpart of the requests channel. Results are published/pushed asynchronously on this channel when the ERE completes the execution of a request. +
The channel is used to publish instances of the +EREResponse++ +subclasses in JSON format. +
Note that this includes the management of errors (see below).

=== Entity Mention

An entity mention represents data submitted to the system by a source system or actor that describes, or refers to, a real‑world entity. An entity mention is always conveyed as part of an entity resolution request and constitutes the subject of the resolution operation. +
An entity mention consists of:

* an *entity mention identifier*, used for correlation and scoping of the request, and
* an *entity representation*, provided as a text‑based serialisation together with its declared MIME type.
This is an example: +
----
{
  "identifier": {
    "request_id": "324fs3r345vxab",
    "source_id": "TEDSWS",
    "entity_type": "http://www.w3.org/ns/org#Organization",
  },
  "content": "epd:ent005 a org:Organization; ...   cccev:telephone \"+44 1924306780\" .",
  "content_type": "text/turtle"
}

----
==== Entity Mention Identifiers

Each entity mention shall be associated with an entity mention identifier. The identifier is a structured value composed of the following triple:

* source_id – identifies the originating system or actor,
* request_id – uniquely identifies the request within the scope of the originating system,
* entity_type – identifies the type of entity being described.
These values are provided by the ERS client and *shall be present* in every entity resolution request. Together, the triple uniquely identifies an entity mention within the scope of the ER System. +
Entity mention identifiers serve the following purposes:

* correlation of asynchronous requests and responses (the ERE specifies with an additional +ere_request_id +field, to deal with multiple requests or responses about the same entity, see below),
* enforcement of idempotent request handling,
* traceability of resolution proposals and decisions across system components.
An entity mention identifier shall not be interpreted as a canonical identifier and shall not carry governance semantics. Its role is limited to request scoping and correlation.

==== Relationship to Canonical Identifiers

Canonical identifiers are not defined or governed within the entity mention identifier itself. The rules governing canonical identifier value derivation and stability are specified in the normative section _Canonical identifier derivation and stability_. +
The components of the entity mention identifier (source_id, request_id, entity_type) are used as inputs to the standardised deterministic derivation rule that defines the canonical identifier value space. Deterministic derivation ensures that identifier values are reproducible across ERS and ERE implementations and across repeated or replayed requests. +
The canonical identifier for an entity mention is established through the clustering outcome produced by the ERE. The cluster identifier generated by the ERE constitutes the canonical identifier exposed by ERS. Identifier generation according to the deterministic rule does not by itself imply cluster membership; canonical status arises only when the ERE assigns an entity mention to a cluster in a valid clustering outcome. +
By relying on a shared deterministic value space, ERSys ensures that identifier values remain stable across asynchronous processing, idempotent handling, provisional issuance under time-budget constraints, and subsequent clustering updates. +
For the normative specification of canonical identifier value derivation and stability guarantees, refer to the section _Canonical identifier derivation and stability_.

=== Entity Mention Resolution Request

This is the main service the ERE provides. An entity resolution request is sent to the requests channel, and it contains details of an entity mention for which the ERE finds equivalence cluster candidates. The ERE replies with a resolution response object (an instance of +EntityMentionResolutionResponse+) sent to the responses channel. +
The following is an example from the LinkML code (see ‘#heading=h.zc69jntu6wnj[The ERE Data Model]’ section). More details about it are explained below. +
----
{
  "type": "EntityMentionResolutionRequest",
  "entity_mention": {
    "identifier": {
      "request_id": "324fs3r345vx",
      "source_id": "TEDSWS",
      "entity_type": "http://www.w3.org/ns/org#Organization"
    },
    "content": "epd:ent005 a org:Organization; ...   cccev:telephone \"+44 1924306780\" .",
    "content_type": "text/turtle"
  },
  "timestamp": "2026-01-14T12:34:56Z",
  "ere_request_id": "324fs3r345vx:01"  <1>
}
----
<1> `ere_request_id` disambiguates multiple requests for the same entity mention; auto-generate with a UUID.

As you can see, the request contains an entity mention, which in turn, has a composite identifier. +
Note on +ere_request_id+: this is an ERE-specific field, which the ERE needs to match responses to requests. In fact, we might have two requests containing the same entity mention and hence, this disambiguation field is needed too. +
For the purposes of idempotent handling, a resolution request is correlated by its entity mention identifier together with any applicable recommended placements (such as rejected canonical identifiers).

=== Entity Mention Resolution Response

This is the counterpart of the resolution request, which the ERE sends to the entity resolution channel asynchronously. This object contains a set of references to candidate clusters, together with confidence scores. The meaning of them is that the input entity is considered equivalent to the referred clusters, with the given score. +
----
{
  "type": "EntityMentionResolutionResponse",
  "entity_mention_id": {
    "request_id": "324fs3r345vx",
    "source_id": "TEDSWS",
    "entity_type": "http://www.w3.org/ns/org#Organization"
  },
  "candidates": [
    {
      "clusterId": "324fs3r345vx-aa32wa",
      "confidenceScore": 0.91,
      "similarityScore": 0.85
    },
    {
      "clusterId": "324fs3r345vx-bb45we",
      "confidenceScore": 0.65,
      "similarityScore": 0.8
    }
  ],
  "timestamp": "2026-01-14T12:34:59Z",
  "ere_request_id": "324fs3r345vx:01"
}
----

The `candidates` list MUST contain at least one entry.
The first entry (`candidates[0]`) MUST be the ERE's top proposed cluster assignment — the candidate the ERE considers most likely equivalent to the input entity mention.
ERS always selects `candidates[0]` as the primary resolution outcome; ordering is therefore normative, not advisory.

[Informative] one way to use multiple canonical identifier candidates is to feed the curation application, so that the user can decide which entity is actually equivalent to the input, or they can reject all the candidates (see below). +
As you can see, the response reports the composite entity ID of the mention it refers to. This isn’t strictly needed, since it could be reconstructed by going back to the original request through +ere_request_id+. Nonetheless, we repeat these data in the response for convenience.

Note that the ERE contract does not concern with returning any entity representations associated to the clusters, e.g., if an organisation O1 might be associated to a cluster CL1, which of canonical entity is CO1, then the ERE will return a cluster ID for CL1, without any representation about the entity CO1 (and, as described above, the cluster ID will be the same as the canonical ID of CO1).

The ERE is the authority to determine the membership of an entity to clusters.

It is the ERS responsibility to manage and govern the canonical entities, including IDs, integration of entity mention memberships, and if necessary canonical representations. +
This follows from the normative derivation rule defined in the section _Canonical Identifier Derivation and Stability_.

==== Score semantics for singleton clusters (Normative)

When the ERE finds no equivalent cluster for the entity mention and creates a new singleton cluster, it shall return a response with a single candidate whose +confidence_score+ and +similarity_score+ are both +0.0+. +
These values indicate the absence of any pairwise comparison: the newly created cluster has no prior members against which a similarity or equivalence assessment can be made. +
A +confidence_score+ of +0.0+ shall not be interpreted as a resolution failure; it is the expected value for a valid singleton outcome. ERS shall accept and record such a response normally.

=== Resolution Request with proposed placements

A resolution request might contain a list of proposed cluster IDs. The ERE might take them into account, but that is not mandatory, the ERE can still decide a different entity classification and it remains the ultimate authority to decide the clustering of an entity. +
This is an example of such request: +
----
{
  "type": "EntityMentionResolutionRequest",
  "entity_mention": {
    "identifier": {
      "request_id": "324fs3r345vx",
      "source_id": "TEDSWS",
      "entity_type": "http://www.w3.org/ns/org#Organization"
    },
    "content": "epd:ent005 a org:Organization; ...   cccev:telephone \"+44 1924306780\" .",
    "content_type": "text/turtle"
  },
  "proposed_cluster_ids": [
    "324fs3r345vx-aa32wa", "324fs3r345vx-bb45we"
  ],
  "timestamp": "2026-01-14T12:34:56Z",
  "ere_request_id": "324fs3r345vx:01"  <1>
}
----
<1> `ere_request_id` disambiguates multiple requests for the same entity mention; auto-generate with a UUID.
Whether the order of elements in +proposed_cluster_ids +is relevant or not depends on the ERE implementation (i.e., it might decide to give more importance to the top elements).

=== ERE timeouts and singleton proposals

An ERE client might place just one element in +proposed_cluster_ids+ and that might be +canonicalID(entityMention.identifier)+ In other words, it can be proposed that an entity mention is binned into a singleton cluster, containing the entity only. +
(Non-normative): we expect the ERS to do this when the ERE doesn’t reply to an initial resolution request within a configured timeout. In fact, in that case, the ERS might decide to continue with the initial entity as the possible canonical one. As above, the ERE doesn’t have any obligation to classify the entity in this proposed way. Furthermore, given the asynchronous nature of the ERE, an answer to the initial request might arrive after the timeout and the client might decide to consider it despite the subsequent singleton request.

=== Resolution Request with Rejections

An entity resolution request can include the parameter +excludedClusterIds+, to indicate that a previous proposed clustering is not deemed valid and alternative resolutions are requested. One use case for this operation is to account for a negative curator’s decision on an automatic alignment. +
This is an example of request with rejections:
----
{
  "type": "EntityMentionResolutionRequest",
  "entity_mention": {
    "identifier": {
      "request_id": "324fs3r345vxab",
      "source_id": "TEDSWS",
      "entity_type": "http://www.w3.org/ns/org#Organization",
    },
    "content": "epd:ent005 a org:Organization; ...   cccev:telephone \"+44 1924306780\" .",
    "content_type": "text/turtle"
  },
  "excluded_cluster_ids": [
    "324fs3r345vx-bb45we",
    "324fs3r345vx-cc67ui"
  ],
  "timestamp": "2026-01-14T12:40:56Z",
  "ere_request_id": "324fs3r345vxab:01"
}
----

As for the proposed placements, rejections are suggestions for the ERE, depending on the implementation, this may or may not consider them, and it may decide to store them to gather heuristic and use it in machine learning procedures.

=== Resolution Request with (possibly multiple) Proposals and Rejections

A request may have both proposed placements and rejections. Both may be used to improve the clustering, by combining the behaviours described above. +
Similarly, the ERE may accumulate subsequent requests with proposed placements or rejections, by considering the merge of all the proposals coming from multiple messages.

=== Update Responses

The ERE may change cluster assignment of entities based on its internal maintenance, periodic reviews of previously computed data, full rebuilds (see below). When this happens, the ERE notifies all subscribing clients by pushing a +EntityMentionResolutionResponse  +message on the response channel. Since there is no request that can be related it, this response has an +ere_request_id +value having a special prefix +‘ereNotification:’+. +
The alternative could be having a completely different type of message that is not a subclass of +EREResponse+ (see the data model below). However, using the convention above allows for using the same response type that is used to react to client requests and keep the ERE contract simpler.

=== (Non-Normative) Full cluster rebuild

The ERE may support internal reprocessing or rebuild operations that trigger re-evaluation of previously computed clustering outcomes. Such operations are entirely internal to the ERE and are not invoked through the asynchronous request channel defined in this contract. +
A rebuild may be scoped to one or more entity types. If no scope is specified, the operation may apply to all entity types managed by the ERE. The exact internal mechanics of rebuild depend on the specific ERE implementation and its resolution strategies. This contract does not prescribe how reprocessing is performed, how intermediate state is managed, or how clustering algorithms are re-executed. +
Reprocessing may be initiated manually by an operator or automatically by the ERE as part of maintenance, optimisation, or algorithm updates.

=== (Normative) Communication of rebuild outcomes

Although rebuild is not triggered via the asynchronous request channel, any change in clustering outcomes resulting from rebuild shall be communicated through the standard responses channel using the same message structures defined for resolution outcomes. +
Rebuild-triggered clustering updates shall follow the same correlation and idempotency rules as regular responses. In particular:

* Updates shall reference the entity mention identifier triad.
* Duplicate or repeated updates shall be processed idempotently.
* The ERS shall record the latest received clustering outcome per entity mention.
This contract does not define rollback semantics, temporal state restoration, or lineage relationships between clusters. The ERE is not required to preserve historical cluster evolution or to expose previous cluster states. +
Rebuild operations may result in clustering changes being published concurrently with new resolution requests. Implementations shall ensure that such interleaving does not violate idempotent processing guarantees or correlation rules. +
The purpose of this section is to clarify that reprocessing is an ERE responsibility, that its effects are propagated through standard outcome messages, and that no additional contract surface is introduced for rebuild control or state rollback.

=== Error Response

An ERE request of any type (resolution, rebuild) might fail, due to problems like a malformed request or an internal malfunction. In this case, the ERE will publish a response object of type +EREErrorResponse+. This is an example: +
----
{

  "type": "EREErrorResponse",
  "ere_request_id": "324fs3r345vx",
  "errorType": "ere.exceptions.MalformedRequestError",
  "errorTitle": "The entity data is missing in the request",
  "errorDetail": "The 'entity' attribute is required in EntityResolutionRequest message",
  "errorTrace": "Traceback (most recent call last):\n  File \"/app/ere/service.py\",\n     line 45, in process_request\n..."  <1>
}
----
<1> `errorTrace` is optional and should not be included in production use.
