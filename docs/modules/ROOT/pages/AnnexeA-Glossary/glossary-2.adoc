== II. Glossary of system-oriented concepts

This section defines system components, actors, operations, and interaction patterns. These terms describe *how the system behaves*, *who performs actions*, and *where responsibilities lie*.
|===
|*Preferred term*|*Definition*|*Scope and use context*|*Alternative terms*

|*Originator*|An external system or process that submits entity mentions or resolution requests.|The originator provides data but does not control resolution outcomes. Used for provenance and traceability.|source system
|*Entity Resolution*|The process of assigning entity mentions to clusters that represent managed identities under available evidence.|Entity resolution operationally creates, updates, or revises cluster membership. It manages system identities and does not assert facts about real-world entities.|identity resolution
|*Entity Resolution Engine (ERE)*|The application component responsible for clustering logic, similarity scoring, confidence scoring, and canonical identity materialisation.|The ERE is the sole authority for determining cluster membership and canonical identity. Its clustering outcomes are binding. It realises the ERS–ERE Technical Contract and maintains the authoritative cluster store.|ER engine, matching engine, resolution engine
|*Entity Resolution Service (ERS)*|The application component responsible for public APIs, client-facing time-budget enforcement, orchestration of resolution requests, and persistence of the latest recorded clustering outcomes.|ERS records and exposes the latest authoritative cluster assignment per mention. It does not govern canonical identity semantics and does not override ERE clustering decisions.|ER service, orchestration service, coordination service
|*Entity Resolution System (ERSys)*|The integrated system composed of ERS, one or more ERE implementations, persistence components, and the link curation application.|Canonical identity in ERSys is engine-authoritative: clusterIds generated by the ERE constitute canonical identifiers. ERS provides bounded exposure, persistence of latest decisions, and synchronisation mechanisms.|ER system, entity resolution platform, ER platform, ER solution
|*ER Engine Contract*|A formal specification defining required interfaces, data structures, and behavioural guarantees for EREs.|Enables independent development, replacement, and parallel operation of multiple engines. It governs interoperability, not internal algorithms.|engine contract, engine interface, engine API contract
|*Cluster Assignment*|The association between an entity mention and a clusterId as determined by the ERE in a valid clustering outcome.|Canonical identity for a mention equals its latest recorded cluster assignment in ERS. Assignment may change over time as the ERE produces new authoritative outcomes.|Automatic Alignment, machine match
|*User Placement (manual alignment)*|A curator-initiated recommendation requesting re-evaluation of a mention’s cluster assignment, expressed as a preferred placement and/or exclusion constraints.|User placement does not directly modify canonical identity. It is forwarded to the ERE as a resolution request variant. The resulting assignment is determined exclusively by the ERE.|Manual Alignment, Link Curation, human review
|*Curator*|A human actor responsible for curating alignments.|Acts through the curation application; does not manipulate engine internals directly.|reviewer, data steward, domain expert, reviewer
|*Link Curation Web Application*|A user-facing application supporting curation workflows.|Provides interfaces for review and decision-making; does not implement resolution logic.|curation UI
|*System of Records*|An immutable store of all submitted entity mentions and associated request metadata.|The System of Records is authoritative for submitted artefacts and provenance only. It is not authoritative for canonical identity or cluster membership.|request log, input record store
|*Decision Store*|A persistence component owned by ERS that stores the latest authoritative cluster assignment per mention and the top N alternatives from the most recent ERE outcome.|The Decision Store contains only the current authoritative state required for exposure and delta computation. It does not maintain canonical lineage or independent identity semantics.|Placement store, decision repository, decision log
|*Resolution Orchestration*|The coordination process by which ERS forwards requests to ERE, handles time budgets, and updates projections.|Covers forwarding, provisional lifecycle, response processing, and delta tracking.|resolution coordination
|*Cluster rebuild (Reclustering)*|A resolution operation that recomputes clusters for all entity mentions registered by the ERE.|Rebuild or reclustering is not an explicit ERS administrative operation. When the ERE emits updated clustering outcomes, ERS records them and exposes changes via standard delta mechanisms. |full rebuild, complete cluster rebuild
|*Re-resolve*|A resolution operation that recomputes cluster membership for a specific entity mention, usually subject to previously recorded rejection constraints or alternative placement. |Used for user actions and corrective processing. Forwarded to ERE for authoritative evaluation. |re-resolution
|*Bulk Refresh (lookup)*|A read-only operation that returns the set of mentions for a given originId whose cluster assignment has changed since the last successful refresh.|Delta computation follows the rule: lastUpdateDate > lastNotificationDate. refreshBulk does not trigger clustering, re-resolution, or engine interaction.|Delta Lookup, Lookup
|*Draft Identifier*|A deterministically derived singleton clusterId issued by ERS when the ERS–ERE execution window expires before an engine response is received.|A provisional identifier is a valid canonical identifier at the time of issuance. It remains valid until confirmed or replaced by a subsequent authoritative ERE outcome.|Provisional Identifier
|*User Action Log*|A read-only log of curator recommendations and related interaction metadata.|The User Action Log supports traceability and potential model training. It does not define or override canonical identity.|Interaction Log
|*Entity Type Configuration*|A system configuration artefact defining how entity mention representations of a given type are interpreted and processed.|Specifies schema expectations and extractor instructions (e.g. XPath, JSONPath, SPARQL). |entity type config, schema config,
|===
