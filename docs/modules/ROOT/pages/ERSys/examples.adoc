= Examples
:description: Annotated request and response examples for the ERS REST API, Curation REST API, and entity type configuration.

This page provides examples demonstrating how to integrate with ERSys.
It covers the most common request and response patterns for the ERS REST API (submitting entity mentions, looking up cluster assignments, retrieving assignment deltas), the Curation REST API (recording curator decisions), and the entity type configuration format used to register new entity types with ERS.

== ERS REST API

=== Submit an Entity Mention

`POST /api/v1/resolve` — submit an organisation mention and receive a canonical or provisional cluster identifier.

.Request
[source,http]
----
POST /api/v1/resolve HTTP/1.1
Content-Type: application/json

{
  "mention": {
    "identifiedBy": {
      "source_id": "demo-source-001",
      "request_id": "org-regensburg-001",
      "entity_type": "ORGANISATION"
    },
    "content_type": "text/turtle",
    "content": "@prefix org: <http://www.w3.org/ns/org#> .\n@prefix epo: <http://data.europa.eu/a4g/ontology#> .\n@prefix cccev: <http://data.europa.eu/m8g/> .\n@prefix epd: <http://data.europa.eu/a4g/resource/> .\n\nepd:entorg-regensburg-001 a org:Organization ;\n    epo:hasLegalName \"Landratsamt Regensburg\" ;\n    cccev:registeredAddress [\n        epo:hasCountryCode \"DEU\" ;\n        epo:hasNutsCode \"DE232\"\n    ] ."
  }
}
----

.Response — canonical resolution (HTTP 200)
[source,json]
----
{
  "identified_by": {
    "source_id": "demo-source-001",
    "request_id": "org-regensburg-001",
    "entity_type": "ORGANISATION"
  },
  "canonical_entity_id": "a3f1c9b2d45e78f0912345678901abcd12345678901234567890abcdef012345",
  "status": "CANONICAL"
}
----

.Response — provisional resolution (HTTP 202)
[source,json]
----
{
  "identified_by": {
    "source_id": "demo-source-001",
    "request_id": "org-regensburg-001",
    "entity_type": "ORGANISATION"
  },
  "canonical_entity_id": "7c3e9db45a12ef890123456789abcde01234567890abcdef12345678901234ab",
  "status": "PROVISIONAL"
}
----

Both canonical and provisional identifiers are 64-character lowercase SHA-256 hex strings.
A `PROVISIONAL` response means the ERE did not respond within the configured time budget.
The provisional identifier is deterministically derived from the mention triad and remains valid until the ERE returns an authoritative outcome.
See xref:AnnexeA-Glossary/glossary-2.adoc[Glossary — Draft Identifier] for the stability guarantees.

=== Look Up Current Cluster Assignment

`GET /api/v1/lookup` — retrieve the current cluster assignment for a previously submitted mention.

.Request
[source,http]
----
GET /api/v1/lookup?source_id=demo-source-001&request_id=org-regensburg-001&entity_type=ORGANISATION HTTP/1.1
----

.Response (HTTP 200)
[source,json]
----
{
  "identified_by": {
    "source_id": "demo-source-001",
    "request_id": "org-regensburg-001",
    "entity_type": "ORGANISATION"
  },
  "cluster_reference": {
    "cluster_id": "a3f1c9b2d45e78f0912345678901abcd12345678901234567890abcdef012345",
    "confidence_score": 0.91,
    "similarity_score": 0.87
  },
  "last_updated": "2025-05-14T10:30:00Z"
}
----

=== Retrieve Assignment Deltas (Bulk Refresh)

`POST /api/v1/refresh-bulk` — returns the set of mentions for a given source whose cluster assignment has changed since the last synchronisation.

.Request
[source,http]
----
POST /api/v1/refresh-bulk HTTP/1.1
Content-Type: application/json

{
  "source_id": "demo-source-001"
}
----

.Response (HTTP 200)
[source,json]
----
{
  "deltas": [
    {
      "identified_by": {
        "source_id": "demo-source-001",
        "request_id": "org-regensburg-001",
        "entity_type": "ORGANISATION"
      },
      "cluster_reference": {
        "cluster_id": "a3f1c9b2d45e78f0912345678901abcd12345678901234567890abcdef012345",
        "confidence_score": 0.91,
        "similarity_score": 0.87
      },
      "last_updated": "2025-05-14T10:30:00Z"
    }
  ],
  "has_more": false,
  "continuation_cursor": null
}
----

Pass `continuation_cursor` from a previous response back in the next request to page through a large delta set.

== Curation REST API

NOTE: The Curation REST API is the backend for the xref:UserGuide/curation-guide-overview.adoc[Curation Web App].
In most scenarios curators interact with the web interface rather than calling the API directly.
These examples are provided for tooling developers and system integrators who need programmatic access.

=== Record a Curator Assignment

`+POST /api/v1/curation/decisions/{decision_id}/assign+` — record a curator's choice to assign a mention to a specific cluster.
The cluster ID must come from the decision's candidate list.

.Request
[source,http]
----
POST /api/v1/curation/decisions/dec-00123/assign HTTP/1.1
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "cluster_id": "a3f1c9b2d45e78f0912345678901abcd12345678901234567890abcdef012345"
}
----

.Response
----
HTTP/1.1 204 No Content
----

ERS records the action in the User Action Log and forwards a re-evaluation recommendation to the ERE.
The ERE determines the final cluster assignment.

[[ers-entity-type-configuration]]
== ERS Entity Type Configuration

The file `src/config/rdf_mention_config.yaml` in the ERS repository defines how entity mention representations are parsed.
Each entity type maps field names to SPARQL property paths (using `/` as a multi-hop separator).

.Annotated structure
[source,yaml]
----
# Namespace prefix registry — used to resolve prefixed names in field paths
namespaces:
  org:   "http://www.w3.org/ns/org#"
  epo:   "http://data.europa.eu/a4g/ontology#"
  cccev: "http://data.europa.eu/m8g/"
  locn:  "http://www.w3.org/ns/locn#"
  # ... add further prefixes here

entity_types:
  ORGANISATION:                        # <1>
    rdf_type: "org:Organization"       # <2>
    entity_label_field: "legal_name"   # <3>
    fields:                            # <4>
      legal_name:  "epo:hasLegalName"
      country_code: "cccev:registeredAddress/epo:hasCountryCode"   # <5>
      nuts_code:    "cccev:registeredAddress/epo:hasNutsCode"
      post_code:    "cccev:registeredAddress/locn:postCode"
      post_name:    "cccev:registeredAddress/locn:postName"
      thoroughfare: "cccev:registeredAddress/locn:thoroughfare"

  PROCEDURE:
    rdf_type: "epo:Procedure"
    entity_label_field: "title"
    fields:
      title:       "dct:title"
      description: "dct:description"
      identifier:  "adms:identifier/skos:notation"
      # ...
----
<1> The entity type key must match the `entity_type` string submitted in resolve requests.
<2> The RDF class URI the parser looks for in the submitted Turtle/JSON-LD content.
<3> The field whose value is used as the human-readable label in the curation UI.
<4> Field-to-path mappings: each key becomes a named field in the parsed representation.
<5> A `/`-separated path indicates a multi-hop SPARQL property path; here, traverse `cccev:registeredAddress` first, then extract `epo:hasCountryCode`.

To register a new entity type, add an entry under `entity_types`, declare its `rdf_type`, choose an `entity_label_field`, and list the field paths.
ERE implementations must handle the same entity type keys.

[[error-response]]
== Error Response

All ERS REST API errors use the same `ErrorResponse` envelope with `error_code` (machine-readable) and `message` (human-readable explanation) fields.
See xref:api-docs/api-integration-guide.adoc#error-reference[API Integration Guide — Error Handling] for the full list of error codes and their meanings.

.Example: mention not found
[source,json]
----
{
  "error_code": "MENTION_NOT_FOUND",
  "message": "No mention found for the supplied triad."
}
----

.Example: idempotency conflict
[source,json]
----
{
  "error_code": "IDEMPOTENCY_CONFLICT",
  "message": "A previous request submitted the same mention triad with different content."
}
----
