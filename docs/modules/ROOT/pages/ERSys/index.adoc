= ERSys Overview
:description: Introduction to the Entity Resolution System — what it does, what it does not do, and where to find documentation for your role.

ERSys is an open-source, scalable entity resolution platform.
It assigns and maintains stable canonical identifiers for entity mentions submitted by external systems,
so that downstream consumers have a consistent identity even as resolution quality improves over time.

== How ERSys Works

Originators submit entity mentions — RDF descriptions of real-world entities such as organisations or procurement procedures — and ERSys returns a stable canonical cluster identifier for each one.
Mentions that describe the same real-world entity are assigned to the same cluster; the `clusterId` is the durable reference downstream systems use.

Resolution is performed by an Entity Resolution Engine (ERE), a pluggable component that groups incoming mentions using similarity algorithms or machine learning.
Different ERE implementations can be used, each potentially applying different resolution algorithms or handling different entity types.
Communication between ERS and any ERE is asynchronous: requests and responses flow through a shared message queue (Redis), which decouples the two components and allows the ERE to operate independently of ERS request timelines.

ERS orchestrates the interaction, enforces response time budgets, and persists the latest assignment per mention.
The ERE is the sole authority for clustering: curator feedback is forwarded to the ERE as a recommendation, not applied directly.

Cluster identifiers are stable — once created, a `clusterId` is never reused for a different cluster.
Assignment, however, can change: if resolution quality improves or a curator recommends a different grouping, a mention may be reassigned to a better-fitting cluster.
This keeps downstream references durable while allowing the system to improve over time.

When the ERE does not respond within the configured time budget, ERS issues a deterministically derived provisional identifier immediately so that downstream processing can continue without blocking.
The mention is queued for asynchronous resolution; the provisional assignment is replaced once the ERE responds.

== What ERSys Does NOT Do

=== System scope

* Does not produce golden records or merge attribute values across mentions.
* Does not clean, normalise, or enrich incoming entity data.
* Does not maintain an authoritative entity registry or ontology.
* Does not provide advanced RBAC beyond the role separation required by the curation use cases.
* Does not manage the machine learning or model lifecycle inside an ERE.

=== ERS vs ERE responsibility

ERS is not an authoritative decision-maker over clustering.
Curator actions (accept, reject, assign) are recorded and forwarded to the ERE as recommendations — they are evidence, not commands.
The ERE determines the final cluster assignment.
ERS projects and exposes the latest authoritative outcome returned by the ERE.
