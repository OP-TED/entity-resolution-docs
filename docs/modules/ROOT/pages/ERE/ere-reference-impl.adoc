= Basic Entity Resolution Engine
:description: A reference implementation of the ERE that conforms to the ERS–ERE Technical Contract.

This page describes the *Basic Entity Resolution Engine* — a reference implementation of the
xref:ERS-ERE-Contarct/index.adoc[ERS–ERE Technical Contract]. It is provided as a concrete,
deployable example that shows one way to build a conformant ERE.

[IMPORTANT]
====
This page is *non-normative*. It describes one implementation, not the only
possible implementation. The sole authoritative specification is the
xref:ERS-ERE-Contarct/index.adoc[ERS–ERE Technical Contract].
====

The source code is available in the
https://github.com/OP-TED/entity-resolution-engine-basic[entity-resolution-engine-basic] repository.

== Overview

The basic ERE is a Python microservice that:

* subscribes to the `ere_requests` channel,
* resolves each incoming entity mention by assigning it to a cluster, and
* publishes the clustering outcome to the `ere_responses` channel.

It demonstrates the *minimum viable contract interaction*: request, resolution, response.
It is intended as a learning resource and a baseline — not as a production-ready solution
for advanced use cases such as curator-guided resolution.

The current configuration supports the *Organisation* entity type
(`http://www.w3.org/ns/org#Organization`).

== Architecture at a Glance

The implementation follows a layered architecture (Cosmic Python style):

[cols="1,3", options="header"]
|===
| Layer | Responsibility

| *Models*
| Pure domain objects: `Mention`, `MentionId`, `ClusterId`, `CandidateCluster`, `ResolutionResult`.
No I/O dependencies.

| *Adapters*
| Infrastructure implementations: DuckDB repositories (mention, similarity, cluster),
Splink probabilistic linker, RDF/Turtle parser.

| *Services*
| Application logic: orchestrates the five-step resolution algorithm. Wraps repositories
and the linker behind abstract port interfaces (Dependency Inversion).

| *Entrypoints*
| External drivers: a Redis queue worker that consumes requests and publishes responses.
A CLI launcher reads environment variables and wires the components together.
|===

All infrastructure concerns — Redis, DuckDB, Splink — live in the *adapters* layer.
Swapping any of them does not affect the domain or service logic.

=== Transport

The basic ERE uses *Redis* as its message broker, via a blocking queue (`BLPOP`).
This is a concrete technology choice, not a contract requirement.
The contract is transport-agnostic; any infrastructure that satisfies the
asynchronous pub/sub semantics defined there is valid.

=== Persistence

Entity mentions, pairwise similarity scores, and cluster assignments are stored in
*DuckDB* — an embedded analytical database that runs in-process. In development mode,
DuckDB operates in-memory. In production mode, it is backed by a file on disk.
No external database server is required.

== The Resolution Algorithm

When a valid `EntityMentionResolutionRequest` arrives, the service executes five steps.

=== Step 1 — Idempotency Check

The service first checks whether the incoming entity mention has already been resolved.
If a cluster assignment already exists for this mention identifier, the cached result
is returned immediately and no further processing occurs.

This satisfies the idempotent processing requirement defined in the contract:
re-submitting the same request produces the same outcome without duplicating state.

=== Step 2 — Blocking

Before comparing the new mention against all known mentions, the service applies
*blocking rules* to reduce the candidate set. Only mentions that share a
common attribute (for example, the same `country_code`) are considered for comparison.

Blocking prevents unnecessary computation and keeps latency bounded as the mention
store grows.

=== Step 3 — Similarity Scoring

The new mention is compared against each blocked candidate using
https://moj-analytical-services.github.io/splink/[Splink], a probabilistic record
linkage library. Splink implements the Fellegi-Sunter model, which computes a
*match probability* for each candidate pair based on agreement across multiple fields
(`legal_name`, `country_code`, `nuts_code`, `post_code`, etc.).

All pairwise scores are persisted as mention-link records, *regardless of whether
they meet the clustering threshold*. Scores below threshold are still used later
when generating the candidate list for the response.

==== Cold Start and Learned Priors

The Splink model requires initial probability estimates (*m/u priors*) for each field.
The basic ERE ships with hand-tuned priors that allow meaningful scoring from the
first request, without any training data. Once 50 mentions have been processed, the
service triggers a background *Expectation-Maximisation* (EM) training pass to refine
these priors automatically. Subsequent requests benefit from the improved estimates.

=== Step 4 — Cluster Assignment

Once similarity scores are available, the service applies a *greedy* assignment rule:

. Find the candidate mention with the highest similarity score.
. If that score meets or exceeds the configured threshold (default: 0.20), assign the
  new mention to the same cluster as that candidate.
. If no candidate meets the threshold, create a new *singleton cluster* whose identifier
  is derived deterministically from the new mention's identifier.

This is an *online* algorithm: decisions are made one mention at a time, in arrival
order. There is no retrospective re-clustering when new evidence arrives. This makes
the algorithm fast and predictable, at the cost of order-sensitivity.

==== Canonical Identifier Derivation

Cluster identifiers are derived deterministically using the rule defined in the contract:

----
SHA256(concat(source_id, request_id, entity_type))
----

Because the cluster identifier of a singleton cluster equals the mention identifier
of its founding member, and that identifier is computed by the same rule, all cluster
identifiers are stable and reproducible across replays and re-submissions.

=== Step 5 — Candidate Generation

Finally, the service constructs the `ResolutionResult` to return to the caller:

. Collect all clusters that have any mention-link to the new mention (including
  below-threshold links).
. Rank them by similarity score, highest first.
. Prune to the top-N (default: 100).
. Ensure the assigned cluster always appears in the list.

The result is serialised as an `EntityMentionResolutionResponse` and published to
the `ere_responses` channel.

== What This Implementation Supports

[cols="1,3", options="header"]
|===
| Feature | Behaviour

| Entity resolution requests
| Fully supported. Each `EntityMentionResolutionRequest` is processed through the
five-step algorithm.

| Idempotent processing
| Supported. Re-submitting a previously resolved mention returns the cached result.

| Deterministic cluster IDs
| Supported. Cluster identifiers conform to the `SHA256(source_id, request_id, entity_type)` rule.

| Error responses
| Supported. Malformed requests or internal failures produce an `EREErrorResponse`.

| Multiple candidates with scores
| Supported. The response includes up to 100 ranked candidate clusters, each with
a `confidence_score` and `similarity_score`.

| Organisation entity type
| Supported. The service is configured for `http://www.w3.org/ns/org#Organization`.
Other entity types can be added via configuration.

| Background model improvement
| Supported. EM training runs automatically in a background thread once sufficient
data is available.
|===

== What This Implementation Does Not Support

The following features are part of the contract but are *not implemented* in the
basic ERE. They are explicitly out of scope for this reference implementation.

=== Proposed and Excluded Cluster IDs (Placements)

The contract allows an `EntityMentionResolutionRequest` to carry:

* `proposed_cluster_ids` — cluster identifiers suggested by a previous resolution or
  by curator input,
* `excluded_cluster_ids` — cluster identifiers the caller considers invalid for this mention.

The basic ERE does not act on either field. When present in a request, they are
accepted at the message level but have no effect on the clustering outcome. The service
makes its own decision based solely on the incoming mention and its internal state.

This is intentional. The contract treats these fields as *advisory*: an ERE is not
required to honour them, and it remains the ultimate clustering authority. The basic
implementation exercises this right by ignoring them, demonstrating that minimum-viable
conformance does not require placement support.

Implementations that wish to incorporate curator feedback should treat these fields
as additional signals in the scoring or assignment step.

=== Spontaneous Update Notifications

The contract defines the `ereNotification:` prefix for `ere_request_id` to signal
that a response was not triggered by a request but by an internal re-clustering event.
The basic ERE does not emit such notifications. Any cluster change that results from
its internal state transitions is not proactively communicated to ERS.

=== Cluster Merging

Once a mention is assigned to a cluster, that assignment is not revised. The basic ERE
does not implement any form of cluster fusion, splitting, or retrospective correction.

== Running the Reference Implementation

The repository includes a Docker Compose configuration for a self-contained environment:

----
git clone https://github.com/OP-TED/entity-resolution-engine-basic.git
cd entity-resolution-engine-basic
docker compose -f infra/compose.dev.yaml up
----

A `demo/` directory contains sample datasets (8, 100, and 1000 entity mentions) and
a script that sends requests and summarises the clustering outcomes.

For configuration, see `config/resolver.yaml` (model parameters and thresholds) and
`config/rdf_mapping.yaml` (entity type field extraction paths). All settings can be
overridden via environment variables.

Refer to the repository README for full setup, configuration reference, and test
execution instructions.
